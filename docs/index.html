Meridian Platform Guide

The design, the architecture, and how to run it on your laptop. This guide grows with the project.

What Meridian is

Meridian is a fictional retailer. This project builds its platform one course module at a time. The part that exists today is the data pipeline: it takes files of orders and support cases, checks every row, and decides whether each row can be trusted.

HLD: the system today

LLD: inside the ingestion job

What happens during meridian ingest

  1. cli.py receives the command and loads settings from config.py.
  2. sources.py reads the three CSVs, from S3 or a local folder, and fingerprints their bytes with SHA-256. The result is a LandingBatch.
  3. pipeline.py runs each rule from rules.py and returns a RunResult. It reads and writes nothing outside memory, so the same input always gives the same answer.
  4. store.py saves the whole result in one database transaction: either all of it lands, or none of it does.

Main data types

These live in models.py.

TypeWhat it represents
LandingBatchOne delivery: its parsed rows and the fingerprint of its content
RecordOne row, plus the problems found in it
FindingOne problem: which rule fired, on which row, and why
RouteWhere a row goes: PUBLISH, HUMAN_REVIEW or REJECT
RunResultThe outcome of a run: PUBLISHED, PAUSED or DUPLICATE, plus all records

The rule to remember: the worst finding wins

A row can trigger several rules, and the most severe one decides its route. REJECT beats HUMAN_REVIEW, and HUMAN_REVIEW beats PUBLISH.

How to read it

Today: data comes in

A delivery moves left to right along the Data row. Run it yourself in the Setup & run tab.

Next: people act on it

The API and dashboard let a reviewer see the review queue and decide a conflict, such as case MCS-502.

Later: AI helps

The assistant answers with citations. The agent calls the same backend functions as tools, and consequential actions wait for human approval.

Data model

Two databases, two purposes. meridian_retail is the trusted system of record seeded from the course SQL pack (read-only for the app). meridian_landing is written by the ingestion pipeline and holds everything it produces: staged rows, rejected rows, review items and a full audit trail.

How 3 files become 7 tables

The pipeline reads 3 CSV files and routes each row by its worst validation finding. The 7 landing tables are the output:

Key design decisions

DecisionWhat we choseWhy
Staging tables mirror CSV structureOne stg_* table per CSV fileNo transformation yet: staging is a clean copy of what passed. Transformation happens later when rows promote to meridian_retail
Rejected rows store the full payload as JSONpayload JSON + reasons JSONThe original data is preserved exactly, even if the schema changes. No data is lost on rejection
Review queue stores the full payload tooSame pattern as rejected_recordsThe reviewer needs to see the exact data the pipeline saw, not a foreign-key reference that might change
No foreign keys in landing tablesLogical relationships only (dashed lines in the ER diagram)The pipeline handles referential integrity in Python (bundle cascades). DB-level FKs would complicate upserts and reject partial deliveries
Retail tables have full constraintsFKs, CHECK constraints, InnoDBThis is the trusted system of record. The database enforces correctness as a second line of defence
One transaction per runengine.begin() wraps all insertsEither the entire run lands or nothing does. No partial state to clean up
Upsert by delete + insertDELETE WHERE key IN (...) then INSERTA re-delivered key replaces the old row. Works identically on MySQL and SQLite (used in unit tests)
Timestamps stored as naive UTCDATETIME, not TIMESTAMPMySQL TIMESTAMP has timezone conversion. Naive UTC is simpler and portable to SQLite in tests

Useful queries

Count rows by route for a specific run 
SELECT
    f.file,
    f.route,
    COUNT(*) AS cnt
FROM ingest_findings f
JOIN ingest_runs r ON r.run_id = f.run_id
WHERE r.status = 'PUBLISHED'
GROUP BY f.file, f.route
ORDER BY f.file, f.route;
Find all rejected rows and why 
SELECT
    record_key,
    file,
    JSON_EXTRACT(reasons, '$[0].rule_id') AS rule,
    JSON_EXTRACT(reasons, '$[0].message') AS reason
FROM rejected_records
ORDER BY id DESC
LIMIT 20;
List open review items with the conflicting dates 
SELECT
    record_key,
    file,
    JSON_EXTRACT(reasons, '$[0].message') AS conflict,
    status
FROM review_queue
WHERE status = 'OPEN'
ORDER BY id;
Check if a delivery was already published (VR-009) 
SELECT run_id, status, source, finished_at
FROM ingest_runs
WHERE content_hash = (
    SELECT content_hash FROM ingest_runs
    WHERE run_id = '<your-run-id>'
)
ORDER BY finished_at;
Join staged orders with the trusted database 
-- Compare staged (landing) orders with trusted (retail) orders
SELECT
    s.order_id,
    s.product AS staged_product,
    r.product AS trusted_product,
    s.delivery_date AS staged_date,
    r.delivery_date AS trusted_date
FROM meridian_landing.stg_orders s
LEFT JOIN meridian_retail.orders r USING (order_id)
LIMIT 10;
Rejection rate by rule across all runs 
SELECT
    rule_id,
    route,
    COUNT(*) AS findings,
    COUNT(DISTINCT run_id) AS runs_affected
FROM ingest_findings
WHERE route IN ('REJECT', 'HUMAN_REVIEW')
GROUP BY rule_id, route
ORDER BY findings DESC;

Access control

The app user meridian has full access to meridian_landing (read + write) but only SELECT on meridian_retail. This is enforced by the grant in 10_landing_grants.sql:

GRANT SELECT ON meridian_retail.* TO 'meridian'@'%';

Attempting a write to meridian_retail fails with: ERROR 1142: DELETE command denied to user 'meridian'

Run Meridian on your Mac

By the end you will have MySQL and a local S3 running in Docker, a sample delivery ingested, and the results in the database. Allow about 10 minutes, plus image downloads the first time.

Steps 1 to 11 and the "Try breaking it" experiment were run on this Mac on 2 November 2026, and the expected outputs are from that run. That test used a temporary copy of the project on other ports, so MariaDB kept running and the brew services commands were not run.

0 of 11 steps done
1

Check your tools

You need Docker Desktop (or OrbStack) running, and uv. You don't need to install Python yourself, because uv fetches Python 3.12 for the project.

docker info --format '{{.ServerVersion}}'
uv --version
Expected output (versions may be newer)
29.8.1
uv 0.13.6 (Homebrew 2026-10-26 aarch64-apple-darwin)

If uv is missing, run brew install uv. If docker info reports an error, open Docker Desktop and try again.

2

Create your settings file

The .env file holds local-only settings: database addresses, the Floci address and dummy AWS keys.

cd ~/Documents/my-projects/learning/scaler/meridian-platform
cp .env.example .env
3

Free up port 3306

Required on this Mac. Homebrew MariaDB is using port 3306, which the project's MySQL container also needs. If you skip this step, make up fails with:

ports are not available: exposing port TCP 0.0.0.0:3306 ... bind: address already in use

Stop MariaDB while you work on Meridian. This doesn't delete its data.

brew services stop mariadb

Then confirm nothing is using the port. This command should print nothing:

lsof -nP -iTCP:3306 -sTCP:LISTEN
Need MariaDB to keep running? Use port 3307 instead

Make these two edits, and don't commit the first one, because CI expects 3306.

  1. In docker-compose.yml, change "3306:3306" to "3307:3306".
  2. In .env, change 127.0.0.1:3306 to 127.0.0.1:3307 in both MERIDIAN_DB_URL and MERIDIAN_TRUSTED_DB_URL.
4

Install the Python dependencies

This creates a .venv folder using the exact versions in uv.lock.

make sync

Start the stack

This starts MySQL, Floci and Adminer, then waits until they are ready. The first start also loads the course data into MySQL, which takes 30 to 60 seconds after the images download. It can wait up to 3 minutes per service before giving up.

make up
Expected last lines

mysql: ready

Run it again to see the duplicate check

Expected change

The file contents have the same fingerprint as a run that already published, so nothing is written to the staging tables again. The attempt is still logged in the audit trail. The counts in the output look the same because the rules still ran.
